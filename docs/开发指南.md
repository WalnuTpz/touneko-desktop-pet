# 开发指南

本文从一份源码工作区开始，介绍本地启动、修改、验证与文档维护。桌宠使用 Electron 主进程管理窗口和系统状态，渲染进程使用原生 JavaScript 控制行为与动画，Python/Pillow 负责准备素材。

## 准备工作区

在 Windows 10/11 上安装 Node.js 22.12.0 或更高版本，以及 Python 3.10 或更高版本。确认 PowerShell 中的 `node`、`npm` 和 `python` 可用，然后在项目根目录执行：

```powershell
node --version
python --version
python -m pip install -r requirements.txt
npm ci
```

`npm ci` 按 `package-lock.json` 安装 JavaScript 依赖。Python 依赖为 Pillow，版本范围由 `requirements.txt` 指定。桌面运行时固定为 Electron `43.2.0`。

源码仓库保存素材 ID 与角色清单，本地另行准备图片：`assets/catalog.json` 的 `staticAssets` 每个 ID 对应 `assets/local/static/<id>.png`，`animatedAssets` 每个 ID 对应 `assets/local/animated/<id>.gif`。当前清单需要 136 张 PNG、21 份 GIF。准备齐全后执行：

```powershell
npm start
```

这条命令先运行素材生成器，再启动 Electron。成功时终端打印“素材准备完成”，随后出现角色和托盘图标。修改 JavaScript、HTML 或 CSS 后，从托盘退出糖猫，再执行 `npm run dev`；这个命令直接启动 Electron，使用已有生成素材。修改素材、素材清单或生成器后，执行 `npm start` 重建素材。

在 WSL 中阅读、编辑和运行纯逻辑测试时使用 Linux 工具，工作副本放在 Linux 文件系统。Windows 窗口、托盘、PowerShell 监测和便携版验收在 Windows 环境执行；Windows 路径通过 `/mnt/<盘符>/...` 访问。

## 修改行为

从用户可见的触发过程定位修改。例如排查“双击之前先播放了一次单击动作”，先确定 Windows 提供的双击间隔如何到达渲染进程，再检查第一次释放、第二次按下和最终双击事件如何取消或执行待确认单击。

行为规则由 `docs/桌宠规则.md` 描述。修改前同时阅读对应实现与测试，明确输入、状态变化和预期结果。实现分为三层：

- 主进程持有窗口位置、显示器、托盘菜单和持久设置，处理系统输入与移动请求。
- 渲染进程持有当前行为、图片帧、方向、最近记录和计时器，决定下一步展示什么。
- 纯逻辑提供抽取、循环次数、计时和运动计算，可直接在 Node 中验证。

跨进程调用由 `src/preload.js` 暴露的 `desktopPet` 接口完成。修改一个规则时，沿这条调用路径更新实际负责它的层；源码集中在 `src/main.js`、`src/renderer.js` 和 `src/core.js`。

修复以可复现的输入和状态为依据。先纠正错误状态、引用或控制流；外部输入在入口处理，内部使用已有不变量。保留错误上下文，避免用默认值、宽泛捕获、重复检查或重试掩盖缺陷。新增处理分支应对应实际需求或已复现失败。

## 修改素材和文案

素材的 ID、行为角色、移动动画与单素材倍率在 `assets/catalog.json` 中维护。改变素材用途时修改角色映射；原始 PNG/GIF 保留在本地，生成器写入 `assets/generated/`。完整的格式示例、倍率计算和视觉检查步骤见[素材说明](../assets/README.md)。

修改气泡文案时，按以下顺序操作：

1. 在 `src/dialogue.js` 修改开场白或动作主题的四条文案。
2. 多个素材共用主题时，在 `assets/catalog.json` 的 `dialogueAliases` 指定主题 ID。
3. 运行以下命令，重建映射、验证文案并更新文档。

```powershell
npm run prepare:assets
node tests/dialogue.test.js
npm run docs:dialogue
```

`docs/气泡文案.md` 是生成结果。开头的说明与排版来自 `scripts/render_dialogue_doc.js`，文案来自 `src/dialogue.js`，当前动作主题来自生成 manifest。更新生成说明时修改脚本后重新生成。

## 验证修改

### 本地检查

完成代码或行为修改后，在项目根目录运行：

```powershell
npm run check
npm test
```

`check` 检查 JavaScript 与 Python 源码语法，在准备角色素材之前即可执行。

`npm test` 先重新生成全部本地素材，再依次执行六个测试文件：

| 验证对象 | 测试覆盖 |
|---|---|
| 纯逻辑 | 加权抽取、最近记录、完整循环、暂停计时、释放速度、减速和反弹 |
| 文案 | 每主题四条文案、开场白、素材主题映射 |
| 素材清单 | 素材角色、帧时长、源文件内容、边界和窗口尺寸限制 |
| 资源格式 | 加密资源往返、路径约束、内容篡改与读取 |
| 渲染状态 | 点击时序、透明区、穿透、全屏暂停和环境权重 |
| 主进程协议 | 全屏坐标换算、逐显示器确认、系统双击设置初始化 |

定位单个问题时可以直接运行对应文件，例如 `node tests/renderer.test.js` 或 `node tests/main.test.js`。测试使用生产源码，在 Electron、DOM 和时钟等外部边界设置替身，以确定性输入验证结果。涉及素材或文案的测试先执行 `npm run prepare:assets`。

### 真实窗口验证

在 Windows 上，从托盘退出普通运行实例，然后执行：

```powershell
npm run prepare:assets
npm run start:smoke
```

`start:smoke` 直接启动 Electron；它本身不会生成素材。成功时进程退出码为 `0`，终端显示“Electron 冒烟测试通过”。截图保存在 `build/smoke-test/`：日常、普通动作、移动和 `150%` 缩放各一张。

冒烟会驱动真实窗口与菜单，检查交互和计时，并通过内部命令验证全屏暂停恢复。它使用独立的临时设置目录。实际全屏自动隐藏在冒烟模式中关闭，因此物理多屏切换与混合 DPI 仍需手工检查：

1. 在普通运行模式下将糖猫拖到第二块显示器，确认移动与任务栏避让采用该显示器的可用区域。
2. 在糖猫所在屏幕打开全屏内容，确认角色隐藏；退出全屏，确认原动作或移动继续。
3. 在另一块显示器切换全屏，确认糖猫所在屏幕的行为保持原样。
4. 在两屏使用不同缩放比例时重复以上步骤，检查隐藏是否作用在正确显示器。

验证记录写清测试命令、运行环境和结果。源码窗口、模拟多屏协议和最终便携包分别对应不同证据。

### 文档修改

纯文档修改核对正文中的命令、菜单、数值和输出路径，并检查相对链接与 `git diff --check`。生成文档还需重新生成并比较结果。文档没有改变运行行为时，验证范围集中在文档与生成关系。

## 常用辅助任务

执行 `npm run catalog:assets` 可根据已生成素材制作尺寸目录图，输出到 `build/asset-catalog/`，用于检查角色比例、宽构图、GIF 各帧和裁切情况。

在独立的源码工作区中执行 `npm run test:demo`，可生成 136 张 PNG 和 21 份 GIF 几何示例，并运行完整测试。生成器通过 `assets/local/.demo-assets` 标记识别示例目录；已有自备素材的目录会保持原样，命令报错退出。需要保留当前素材时，另取一份源码运行示例测试。

GitHub Actions 在 Windows 上安装依赖，依次执行 `npm run check` 与 `npm run test:demo`。这些示例验证行为和素材处理，角色外观仍使用自行准备的表情包进行窗口验收。

将源码与本地素材制成 Windows EXE 的完整步骤在[本地构建](本地构建.md)。录制现有功能时使用[演示脚本](演示脚本.md)安排镜头。

## 排查启动问题

| 现象 | 原因与处理 |
|---|---|
| 提示“缺少素材” | 按错误中的 ID 和格式补齐 `assets/local/` 对应文件，再运行 `npm run prepare:assets` |
| 提示缺少 `PIL` | 为执行 npm 脚本所用的 `python` 运行 `python -m pip install -r requirements.txt` |
| 提示无法读取生成素材 | 在根目录执行 `npm run prepare:assets`，再启动 Electron |
| 直接运行 `dev` 后素材仍是旧的 | `dev` 使用已有生成结果；执行 `npm start` 更新素材 |
| 启动未出现新窗口 | 查看现有托盘实例；重复启动保持原实例状态 |
| 冒烟报告全屏监测错误 | 在 Windows 终端查看完整错误，核对 `powershell.exe` 和 `scripts/fullscreen-monitor.ps1` 是否可读；打包版本还会校验助手脚本内容 |

## 维护文档

文档按读者的任务划分。根 README 提供项目概览、最短启动路径和重要入口；使用指南讲完整操作；开发指南讲修改与验证；设计说明讲概念、数据流和原因；行为规则集中记录精确参数；素材说明和构建指南承接两个独立的工程流程。气泡文案由源码生成，演示脚本安排录制。

修改行为时，同步更新规则、相关测试和受影响的使用或设计说明。调整命令和构建流程时更新操作步骤。规格与实现出现差异时，结合已确认需求和提交记录查明来源。

写作先说明读者要完成什么，再给出概念、步骤、结果和必要原因。正文直接解释当前任务所需知识；普通文件名、配置项与函数名使用行内代码。链接用于切换到另一个完整任务或查阅额外细节，同一段落中无需反复导航。写出明确事实与适用条件，删除辩解、免责套话和对读者的反复提醒。

本次文档组织参考了四类官方实践：

- [React 文档](https://react.dev/reference/react) 将专题学习与 API 参考分开。Thinking in React 用一个实例逐步建立概念；这里用一次点击、一次移动和一次全屏切换解释状态与数据流，精确参数集中到行为参考。
- [Next.js 文档](https://nextjs.org/docs) 包含入门教程、任务指南、API 参考、词汇表与架构说明。其安装页按环境、命令、文件内容和运行结果展开；这里的使用与开发指南同样写出前置条件、操作和可观察结果。
- [Vite 文档](https://vite.dev/guide/) 将特性、构建、部署和排错放进指南，另设配置与 API 参考；Why Vite 从问题解释设计选择。这里将素材处理与成品构建写成独立流程，并解释逐帧播放、亚像素累计和角色清单的原因。
- [vLLM 的架构说明](https://docs.vllm.ai/en/latest/design/arch_overview/) 位于开发指南，整个文档体系另有用户指南、基准测试、API 与 CLI 参考。架构篇先解释入口、进程职责和通信，再定位源码；这里按同样顺序解释桌宠进程，把测试与成品验收放到各自操作流程中。

项目规模适合一层主题文档：命令说明放在实际操作步骤旁，设置说明放在使用指南中，源码定位放在概念解释之后。行为参数集中在一篇参考中，开发者可以从任务入口逐步读到具体原理。
